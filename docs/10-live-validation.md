# 🧪 장애·복구 시나리오와 실행 기록

발표·복습용 **5가지 장애 시나리오의 실행 계획과 결과를 채우는 문서**입니다. 계획과 실제 실행을 구분하고, 각 시나리오의 명령·콘솔 작업·로그·캡처를 같은 번호로 연결합니다.

현재 5가지 의도적 장애 훈련은 **모두 미실행**입니다. 초기 배치 때 관찰한 CA 노드 4→5 확장은 실제 운영 관찰이며, 아래 SC-03의 부하 증가·축소 훈련을 완료한 것으로 보지 않습니다. 현재 성공 결과는 [VALIDATION](VALIDATION.md)에 있습니다.

구체적인 GUI·명령·부하·격리 실습·DB 복원 실행 순서는 [교육 복습노트_검증 및 시나리오](learning/교육%20복습노트_검증%20및%20시나리오.md)에 있습니다. 이 문서는 각 훈련의 계획·실제 결과를 채우는 기록판으로 사용합니다.

## 1. 5가지 시나리오 포함 여부와 상태

| ID | 시나리오 | 기존 문서에 있던 내용 | 이번에 마련한 자리 | 훈련 상태 |
| :--- | :--- | :--- | :--- | :--- |
| SC-01 | 잘못된 이미지 → 버전 복구 | 이미지 digest·이전 이미지 복구 PR 설명 | 실패 조건·탐지·복구·재검증 기록 | 계획 / 미실행 |
| SC-02 | 특정 API 오류 → 로그 분석·수정 | 일반 로그 점검만 있고 독립 시나리오 없음 | API·증상·로그 근거·수정·회귀 검사 기록 | 계획 / 미실행 |
| SC-03 | 부하 증가 → 확장·축소 | HPA/CA 설명·초기 자원 부족 확장 관찰 | 동일 부하 조건·응답·Pod/노드 증감·축소 기록 | 계획 / 미실행 |
| SC-04 | DB 연결 차단 → 연결 복구 | 비밀번호 회전 설명은 있으나 연결 차단 시나리오 없음 | 차단 범위·DB/Probe·재연결·데이터 영향 기록 | 계획 / 미실행 |
| SC-05 | 데이터 복원 → 데이터·앱 확인 | 별도 RDS 복원 실습 가이드 | 기준 데이터·별도 복원·앱 기능·시간 기록 | 계획 / 미실행 |

이 문서의 입력란은 **작성할 항목**이며 이미 확보한 캡처·측정값을 의미하지 않습니다. 시나리오 절차를 작성하거나 운영 환경을 재시작한 것만으로 의도적인 장애·부하·복원 훈련을 실행했다고 기록하지 않습니다.

## 3. SC-01 · 잘못된 이미지와 버전 복구

**확인할 질문:** 실행 불가능하거나 준비되지 않는 이미지 변경을 탐지하고, 이전 정상 버전으로 복구할 수 있는가?

**예정 흐름:** 정상 버전 기록 → 승인한 실습용 실패 이미지 조건 준비 → 배포 또는 사전 검사 차단 관찰 → 이벤트·로그로 원인 확인 → 정상 이미지 복구 PR → 배포·기능 재검증.

현재 릴리스 검사가 잘못된 이미지를 배포 전에 차단하면 **차단 검증 성공**으로 별도 기록합니다. 이를 실제 배포 후 롤백 성공과 혼동하지 않습니다. 장애를 만들기 위해 main 보호·필수 검사를 임의로 우회하지 않습니다. 실패 주입 방법은 별도 검토 후 채웁니다.

## 4. SC-02 · 특정 API 오류와 로그 분석·수정

**확인할 질문:** 화면이 열려도 특정 기능만 실패할 때, 실패 서비스와 원인을 찾아 같은 요청을 정상화할 수 있는가?

**예정 흐름:** 정상 요청·응답 기록 → 범위를 제한한 API 실패 재현 → ALB/Gateway/대상 서비스·의존성 구분 → 로그로 가설 확인 → 수정 PR·검사·승인 배포 → 동일 조건 재호출·관련 기능 회귀 검사.

예상한 401·403·재고 부족 같은 업무 거부와 의도치 않은 5xx를 구분합니다. 서버 내부 오류를 만들지 않은 권한 검사 결과만으로 “서버 장애 복구”를 완료 처리하지 않습니다.

## 5. SC-03 · 부하 증가와 확장·축소

**확인할 질문:** 같은 조건으로 부하를 주었을 때 요청 품질과 Pod·노드 수가 어떻게 변하고, 종료 후 안정 상태로 돌아오는가?

**예정 흐름:** 기준 측정 → 재현 가능한 부하 적용 → 응답시간·오류율·CPU·HPA 관찰 → Pending이 생기면 CA 확인 → 부하 종료·부하 자원 정리 → Pod·노드 축소 및 기능 확인.

현재 HPA 대상은 **member**, 최소 1·최대 3·CPU 목표 60%입니다. 노드 전체 범위는 4~5대입니다. 상품 API에만 부하를 주고 회원 HPA의 확장을 기대하지 않도록 대상 경로와 지표를 맞춥니다. 배치 여유가 있으면 HPA가 늘어도 CA는 늘지 않을 수 있습니다.

## 6. SC-04 · DB 연결 차단과 연결 복구

**확인할 질문:** DB에 연결할 수 없을 때 앱의 준비 상태·요청·로그가 어떻게 변하고, 연결 복원 후 데이터 기능이 정상화되는가?

**예정 흐름:** 정상 DB 조회·테스트 데이터 기록 → 승인한 범위의 연결 실패 주입 → DB/네트워크/자격증명 원인 구분 → 영향·Probe 관찰 → 원래 연결 설정 복원 → 앱 새 연결·상품·주문·기존 데이터 확인.

**DB 비밀번호 회전과 네트워크 연결 차단은 다른 훈련입니다.** 공유 DB 보안그룹을 수정하면 여러 서비스에 영향을 줄 수 있으므로, 대상·허용 시간·정확한 원복 설정을 확정한 뒤 주입 방법을 작성합니다. RDS를 공인으로 전환하거나 전체 접근을 허용하는 방법으로 복구하지 않습니다.

**완료 기준:** 연결 설정이 정상 기준으로 돌아오고, 앱이 DB를 다시 사용하며, 합의한 기능·데이터 확인이 통과해야 합니다. Secret Ready만으로 DB 연결 복구를 완료 처리하지 않습니다.

## 7. SC-05 · 데이터 복원과 데이터·앱 확인

**확인할 질문:** 백업으로 별도 DB를 복원했을 때 기준 데이터가 돌아오고, 그 데이터를 앱이 사용할 수 있는가?

**예정 흐름:** 기준 데이터·시점 기록 → 스냅샷 → 다른 이름의 비공개 DB 복원 → 읽기 대조 → 별도 테스트 앱으로 연결·기능 확인 → 실습 자원 정리.

기본 복원 가이드는 운영 DB를 유지하고 **클라이언트 읽기 조회**로 확인합니다. 앱 확인을 추가하려면 별도 namespace·Secret·검증용 앱과 변경·복원 절차를 먼저 설계합니다. 운영 앱의 DB_HOST를 무작정 바꾸지 않습니다. 스키마 자동 갱신·주문 워커가 복원 데이터를 변경할 수 있으므로 대조 전후 시점을 기록합니다.

| 계획 입력란 | 작성할 내용 |
| :--- | :--- |
| 기준 DB·테이블·테스트 데이터·스냅샷 시점 | 작성 예정 |
| snapshot ID·별도 복원 DB ID·보관 계획 | 작성 예정 |
| 복원 명령 또는 콘솔 작업 | [기존 복원 가이드](08-rds-restore-lab.md)를 검토 후 기입 |
| SELECT 등 데이터 대조 방법 | 작성 예정 — 원문 비밀번호·개인정보 제외 |
| 별도 테스트 앱·연결 방법·예상 기능 | 작성 예정 |
| 앱 데이터 변경 통제·원복·정리·비용 | 작성 예정 |

| 실행 결과 입력란 | 실제 기록 |
| :--- | :--- |
| 스냅샷 / 복원 요청 / available / 기능 확인 시각 | 미실행 |
| 원본·복원 endpoint 구분 | 미기록 |
| 스키마·행 수·상품·주문 기준 데이터 대조 | 미검증 |
| 별도 앱의 상품 조회 등 기능 확인 | 미검증 |
| 운영 DB·운영 앱 영향 여부 | 미기록 |
| 복구 시간·데이터 시점 차이·재발 방지 | 미측정 |
| 실습 DB·앱·Secret·Pod·스냅샷 정리 | 미기록 |
| 증거 링크 / 캡처 파일 | SC-05: 추가 예정 |

**완료 기준:** 다른 endpoint의 복원 DB와 기준 데이터가 확인되고, 계획한 별도 앱 기능까지 검증돼야 합니다. DB만 available이면 “복원 자원 생성”, SELECT만 확인했으면 “데이터 확인”으로 단계별 기록하고 앱 검증은 미완료로 남깁니다.

## 8. 증거·결과를 남기는 방식

각 시나리오의 **증상·영향 → 증거 → 원인 → 해결 → 같은 조건 재검증 → 재발 방지**를 한 묶음으로 기록합니다. 발생·탐지·복구 시각, 적용한 버전, 명령·콘솔 변경, 오류 수·복구 소요 시간을 포함합니다.

캡처는 `sc-01-before.png`, `sc-01-failure.png`, `sc-01-recovered.png`처럼 같은 ID로 묶고 [EVIDENCE](EVIDENCE.md)에 실제 파일 링크를 추가합니다. 현재 해당 파일들은 아직 없습니다. 완료하면 [VALIDATION](VALIDATION.md)에 결과·시점·근거 링크를 추가하고 이 문서의 상태를 갱신합니다.

의도적 장애는 **장애 훈련**, 실제 구축 중 발생한 오류 해결은 **트러블슈팅**으로 구분합니다. 이미 수행한 초기 확장·로그인·주문·메일 검증을 새로운 장애 훈련의 증거로 재사용하지 않습니다.
