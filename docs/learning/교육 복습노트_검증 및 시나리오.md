**직접 사이트·AWS 콘솔·Argo CD·Grafana를 열고, 필요한 명령을 순서대로 실행하면서 검증 증거를 모으는 실습서입니다.** 기존 환경이 실행 중인 상태에서 시작합니다. 개념·최초 구축 설명은 [기존 교육·복습 노트](STUDY-NOTES.md)를 함께 읽습니다.

## 2. 문서를 GitHub에 올리기

## 4. 쇼핑몰·Postman·S3로 실제 기능 검증

Postman Desktop의 로컬 작업 공간을 사용합니다. URL·ID는 환경변수로 두고 비밀번호·token은 local/sensitive 또는 Vault로 관리합니다. 공유·export 자료에는 인증값을 포함하지 않습니다.

### 4-1. GUI · 권한·상품·웹 주문

1. 비로그인 창에서 상품 목록을 봅니다. 관리자 화면 접근은 로그인 유도·접근 제한이어야 합니다.
2. 필요하면 테스트 일반 회원을 가입시켜 로그인·관리자 접근 거부를 확인합니다. 이미 사용하는 이메일은 중복 가입에 사용할 수 없습니다.
3. 관리자 `admin`으로 로그인해 상품명 `LAB-실제session`, 가격 1000, 재고 10, 테스트 이미지로 등록합니다.
4. 상품 ID를 확인하고 새 상품을 캡처합니다. S3 콘솔 → 상품 버킷 → `products/`에서 업로드 시각·객체를 대조하고 실제 이미지 URL을 엽니다.
5. 웹에서 1개 주문하고 상품을 **재조회**합니다. 재고 9와 웹 주문 ID를 기록합니다.

**캡처 F01:** 권한 제한. **F02:** 새 상품·이미지·재고 10. **F03:** 웹 주문 후 재고 9·주문 내역. 과거 ID 1이 아니라 이번에 생성한 ID를 사용합니다.

메일 검증 주문은 SES에서 확인된 이메일의 회원으로 진행합니다. 현재는 관리자 이메일이 인증된 주소이므로 관리자를 사용할 수 있습니다. 일반 회원의 새 이메일·Gmail `+별칭`도 SES sandbox에서는 별도 인증이 필요할 수 있습니다. 미인증 주소의 실패를 앱 정상 주문 검증과 섞지 않습니다.

### 4-2. Postman GUI · 로그인과 요청 변수

로컬 Environment `validation-soldesk`를 만들고 `base_url=https://server.aws-yjeee.com`, 이번 `product_id`를 설정합니다. Collection 이름은 `DevOps Validation`으로 둡니다.

| 요청 | Body / 설정 | 기대 결과 |

| POST `{{base_url}}/member-service/member/doLogin` | raw JSON에 본인 loginId·password | 200, token 발급 |

## 5. 주문 ID에서 DB·메일 이벤트까지 따라가기

### 5-1. 명령 + MySQL · 읽기 대조

RDS는 비공개이므로 외부 Workbench 연결을 위해 public access를 켜지 않습니다. 아래는 EKS 안의 임시 클라이언트를 사용합니다. 공간이 부족하면 앞선 정상 상태·자원부터 확인합니다.

```powershell
kubectl run db-inspect -n soldesk --image=mysql:8.4 --restart=Never --command -- sleep 3600
kubectl wait pod/db-inspect -n soldesk --for=condition=Ready --timeout=180s
$dbEndpoint=terraform '-chdir=terraform' output -raw db_address
kubectl exec -it db-inspect -n soldesk -- mysql -h $dbEndpoint -u admin -p ordermsa
```

`-p` 뒤에 암호를 쓰지 않고 숨겨진 MySQL 입력창에 입력합니다. 필요한 원문 비밀번호는 본인 콘솔의 Secrets Manager에서만 확인하며 캡처하지 않습니다. 비밀번호가 회전됐다면 현재 Secret과 사용 시점을 확인합니다.

MySQL에서 이번 ID를 직접 넣고 실행합니다. 테이블·컬럼이 다르면 SHOW 결과를 먼저 확인합니다.

```sql
SELECT @@hostname, DATABASE(), CURRENT_TIMESTAMP;
SHOW TABLES;
DESCRIBE product;
DESCRIBE `ordering`;
DESCRIBE order_outbox;
SET @product_id = 123;
-- 123은 예시입니다. 이번 상품 ID로 바꾼 뒤 SELECT를 실행합니다.
SELECT id,name,price,stock_quantity FROM product WHERE id=@product_id;
SELECT id,member_id,product_id,quantity,order_status
FROM `ordering` WHERE product_id=@product_id ORDER BY id;
SELECT id,order_id,status,attempts FROM order_outbox
WHERE order_id IN (SELECT id FROM `ordering` WHERE product_id=@product_id);
```

정상이라면 수량 1·2의 두 주문과 재고 7이 연결됩니다. 동일 요청 반복으로 세 번째 주문이 추가되면 안 됩니다. Outbox의 `id`가 메일 eventId입니다. 수신 이메일·본문·비밀번호는 SELECT·캡처에서 제외합니다. **캡처 D01:** 같은 productId·orderId의 데이터와 Outbox eventId.

### 6-3. 패널 6개를 하나씩 만들기

| 패널 제목 | PromQL | 표현·단위 | 읽는 의미 |
| :--- | :--- | :--- | :--- |
| 앱 수집 상태 | `up{namespace="soldesk"}` | Table 또는 Stat, unit none | 앱·Pod별 수집 성공 1 |
| Deployment 준비 수 | `kube_deployment_status_replicas_available{namespace="soldesk"}` | Time series, count | 현재 요청 가능한 replica 수 |
| Pod CPU 사용 | `sum by(pod)(rate(container_cpu_usage_seconds_total{namespace="soldesk",container!="",container!="POD"}[2m]))` | Time series, CPU cores | 0.5는 대략 반 코어 사용 |
| Pod 메모리 | `sum by(pod)(container_memory_working_set_bytes{namespace="soldesk",container!="",container!="POD"})` | Time series, bytes IEC | 실제 메모리 추이·한도와 비교 |
| 사용자 HTTP 요청률 | `sum by(service)(rate(http_server_requests_seconds_count{namespace="soldesk",uri!~"/actuator.*"}[2m]))` | Time series, req/s | Probe를 제외한 요청 변화 |
| HPA 현재 Pod 수 | `kube_horizontalpodautoscaler_status_current_replicas{namespace="soldesk"}` | Time series, count | member 확장·축소 추이 |

CPU·메모리·HTTP series가 없다면 Prometheus에서 원 지표 이름을 먼저 검색합니다. 실제 노출 라벨에 `service`가 없으면 `pod` 등 확인한 라벨로 집계합니다. No data를 무조건 0으로 바꾸지 않습니다. HTTP 지표는 실제 요청을 만든 뒤 두 번 이상의 수집 주기를 기다립니다.

추가 패널로 `sum(kube_node_status_condition{condition="Ready",status="true"})`를 넣어 Ready 노드 수를 봅니다. k6의 p95 응답시간은 뒤의 부하 실습 결과로 남깁니다. 앱 histogram bucket이 노출되는지 확인하지 않고 Prometheus p95 패널이 된다고 가정하지 않습니다.

```powershell
./scripts/ops/Start-DeployCheckRunner.ps1

# 이미 queued/running인 검사가 없을 때만:
gh workflow run deploy-check.yml --ref main
```

Actions에서 verify job을 열어 OIDC·EKS 연결·실제 검증 단계를 읽습니다. 완료 후 해당 이름의 Pod·등록 Secret을 정리합니다. **P04:** 성공 job·검사 항목. 실패하면 먼저 현재 main revision과 Argo 상태를 대조합니다. 이 검사는 주문 생성·DB 복원을 대신하지 않습니다.

## 8. SC-01·02의 별도 실습 Gateway 준비

**범위:** 실제 프로젝트의 Gateway 이미지를 `devops-lab`에 한 개 실행합니다. production의 `soldesk`·Ingress·Argo 선언을 바꾸지 않습니다. 이 실습은 같은 EKS 자원을 사용하므로 남는 메모리·Pod 자리를 먼저 확인합니다. 부족하다고 운영 Pod를 지우지 않습니다.

### 8-1. 명령 · 이미지·namespace·임시 JWT Secret

```powershell
kubectl top nodes
kubectl get pods -A
$gatewayImage=kubectl get deployment apigateway-depl -n soldesk -o jsonpath='{.spec.template.spec.containers[0].image}'
kubectl get namespace devops-lab
# 위 조회가 정상적으로 NotFound이고 이번 전용 실습 namespace가 없을 때만:
kubectl create namespace devops-lab
```

Gateway가 서명 설정을 읽을 수 있도록 필요한 JWT 값만 메모리에서 전달합니다. 다음 블록의 값·환경변수를 출력하거나 파일에 저장하지 않습니다. Secret의 Base64는 암호화가 아닙니다.

```powershell
$source=kubectl get secret my-app-secrets -n soldesk -o json | ConvertFrom-Json
$labSecret=@{apiVersion='v1';kind='Secret';metadata=@{name='lab-jwt';namespace='devops-lab'};type='Opaque';data=@{JWT_SECRET=$source.data.JWT_SECRET}}
$labSecret | ConvertTo-Json -Depth 8 -Compress | kubectl apply -f -
$source=$null; $labSecret=$null
```

**의미:** 운영 앱을 바꾸지 않고 실습 Gateway의 JWT 검증 설정만 준비합니다. 다음 작업은 공개 상품 조회이며 로그인 token을 출력할 필요가 없습니다.

### 8-2. 직접 작성 · 작은 실습 YAML

VS Code에서 `.tools/gateway-lab.yaml`을 직접 만듭니다. 아래 `REPLACE_WITH_CURRENT_GATEWAY_IMAGE`는 방금 `$gatewayImage`에서 확인한 전체 이미지 주소·digest로 바꿉니다. `.tools`는 현재 Git에서 제외됩니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway-lab
  namespace: devops-lab
spec:
  replicas: 1
  selector:
    matchLabels: {app: gateway-lab}
  template:
    metadata:
      labels: {app: gateway-lab}
    spec:
      automountServiceAccountToken: false
      containers:
        - name: gateway
          image: REPLACE_WITH_CURRENT_GATEWAY_IMAGE
          ports: [{containerPort: 8080}]
          resources:
            requests: {cpu: 100m, memory: 256Mi}
            limits: {cpu: '1', memory: 600Mi}
          env:
            - name: JWT_SECRET
              valueFrom:
                secretKeyRef: {name: lab-jwt, key: JWT_SECRET}
          startupProbe:
            httpGet: {path: /actuator/health/liveness, port: 8080}
            periodSeconds: 10
            failureThreshold: 18
          readinessProbe:
            httpGet: {path: /actuator/health/readiness, port: 8080}
            periodSeconds: 10
```

Gateway가 찾는 서비스 이름을 실제 soldesk 서비스에 연결합니다. ExternalName은 DNS 별칭이며 새 DB·백엔드를 만드는 명령이 아닙니다. 여기서는 HTTP 상품 조회만 사용합니다.

```powershell
kubectl create service externalname product-service -n devops-lab --external-name=product-service.soldesk.svc.cluster.local
kubectl create service externalname member-service -n devops-lab --external-name=member-service.soldesk.svc.cluster.local
kubectl create service externalname ordering-service -n devops-lab --external-name=ordering-service.soldesk.svc.cluster.local
kubectl apply -f .tools/gateway-lab.yaml
kubectl rollout status deployment/gateway-lab -n devops-lab --timeout=300s
kubectl expose deployment gateway-lab -n devops-lab --port=80 --target-port=8080 --name=gateway-lab
```

기존 자원이 있으면 AlreadyExists를 무시하고 덮어쓰기 전에 실습 소유 자원인지 확인합니다. 별도 창에서 port-forward를 켭니다.

```powershell
kubectl port-forward service/gateway-lab -n devops-lab 18080:80
```

Postman의 별도 Environment `validation-lab`에서 `base_url=http://127.0.0.1:18080`로 설정하고 GET `{{base_url}}/product-service/product/list`를 보냅니다. 200·상품 JSON이어야 합니다. 도메인을 잘못 선택해 운영 요청과 혼동하지 않습니다. **캡처 L01:** URL·200·실습 Pod·정상 namespace.

## 9. SC-01 · 잘못된 이미지 → 진단·버전 복구

### 9-1. 명령 · 정상 이미지 기록 후 실패 이미지 지정

8단계가 정상인 상태에서 진행합니다. 현재 Git의 이미지가 아닌 **실습 Deployment만** 변경합니다.

```powershell
$normalImage=kubectl get deployment gateway-lab -n devops-lab -o jsonpath='{.spec.template.spec.containers[0].image}'
$badImage='193644343848.dkr.ecr.ap-northeast-2.amazonaws.com/apigateway:missing-lab-'+$session
```

**예상:** 새 Pod가 ErrImagePull/ImagePullBackOff, rollout 대기·timeout. 이 timeout은 이 단계에서 의도한 관찰 결과입니다. 새 이미지가 실행되지 않으므로 앱 로그가 없을 수 있습니다. 이때는 Pod Events가 우선입니다.

단일 replica의 기본 RollingUpdate는 기존 정상 Pod를 유지할 수 있습니다. 따라서 API가 계속 200일 수 있습니다. **“rollout 실패”와 “사용자 서비스 중단”을 구분**해 기록합니다. 짧은 timeout이 Deployment의 자동 rollback을 수행하는 것은 아닙니다.

### 9-2. GUI · 장애 화면·지표

AWS EKS → Resources → namespace `devops-lab` → Deployment·Pod 상태를 확인합니다. Pod 상세 Events를 보고, Grafana Explore에서 아래를 조회합니다.

### 9-3. 명령 · 정상 digest로 복구

```powershell
kubectl set image deployment/gateway-lab "gateway=$normalImage" -n devops-lab
```

### 9-4. 선택 · 승인 GitOps 롤백까지 확장

정상 검증된 릴리스가 두 개 이상이고 ECR에 이전 digest가 남아 있을 때만 [롤백 절차](../ROLLBACK.md)를 진행합니다. GitHub에서 이전 commit의 release.json을 읽고 현재 DB 호환성을 검토합니다. 내부 러너를 준비하고 복구 PR의 팀원 승인·병합 → Argo revision·image·기능 확인까지 기록합니다.

정상 릴리스가 하나뿐이면 이 하위 단계는 미실행으로 둡니다. 잘못된 manifest를 강제로 main에 넣거나 필수 검사를 우회해 장애를 만들지 않습니다. **SC-01-gitops:** 복구 PR·승인·실제 반영 근거를 별도로 추가합니다.

## 10. SC-02 · 특정 API 오류 → 로그 분석·설정 수정

**재현하는 문제:** 실제 Gateway의 상품 서비스 DNS 연결 설정이 잘못되어 특정 API가 5xx가 되는 의존성 오류입니다. Java 비즈니스 로직 버그를 수정한 실습이라고 표현하지 않습니다.

```powershell
kubectl get service product-service -n devops-lab -o yaml
```

### 10-2. Postman·로그 · 실패 계층 찾기

1. 같은 상품 GET을 보내 실제 HTTP status·응답 시각을 적습니다. 500/502/503 등 관찰한 값을 그대로 씁니다.
2. GET `http://127.0.0.1:18080/actuator/health/liveness`도 확인합니다. Gateway 자체는 살아 있으면서 특정 의존 API만 실패할 수 있습니다.
3. 아래 로그에서 DNS·연결 실패와 요청 시각을 대조합니다.


**캡처 SC-02-failure:** URL·status·시각·원인 로그·잘못된 별칭. 실제 운영 URL은 별도로 정상인지 확인해 영향 범위를 구분합니다.

## 11. SC-03 · 실제 부하 → HPA·CA·축소 관찰

**대상:** 현재 HPA가 붙은 member 서비스입니다. 상품 GET만 반복하면 회원 CPU HPA가 늘지 않을 수 있습니다. 테스트 일반 회원의 존재하는 loginId로 **틀린 비밀번호 로그인 요청**을 보내 비밀번호 비교 CPU 작업을 만듭니다. 실제 관리자·고객 비밀번호를 부하 파일에 넣지 않습니다.

### 11-1. GUI · 도구·측정 기준

Grafana 공식 k6 문서에서 본인 Windows용 k6 설치를 준비합니다. Postman으로 테스트 회원의 잘못된 비밀번호 요청이 이 코드에서 **400**인지 먼저 확인합니다. 400 업무 거부를 서버 5xx 장애와 구분합니다.

VS Code에서 `.tools/member-load.js`를 직접 만듭니다. 이 파일은 부하 요청만 수행하며 인프라를 구성하지 않습니다.

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

http.setResponseCallback(http.expectedStatuses(400));
export default function () {
  const r = http.post(
    'https://server.aws-yjeee.com/member-service/member/doLogin',
    JSON.stringify({loginId: __ENV.LAB_LOGIN_ID, password: 'deliberately-wrong-for-load'}),
    {headers: {'Content-Type': 'application/json'}, tags: {name: 'member-password-check'}}
  );
  check(r, {'expected business rejection 400': x => x.status === 400});
  sleep(0.2);
}
```

**의미:** k6의 가상 사용자(VU)가 로그인 비교 작업을 반복합니다. expectedStatuses는 예상한 400을 부하 도구의 실패율에서 구분할 뿐, 서버의 5xx를 성공으로 바꾸지 않습니다. p95는 요청의 95%가 그 시간 이내였다는 지연 지표입니다.

### 11-2. 명령 + Grafana · 단계적으로 부하

먼저 실험 시각·기본 Pod·노드 수를 기록합니다. 별도 PowerShell에서는 `kubectl get hpa ... --watch`, Grafana에서는 6단계 대시보드를 켭니다.

```powershell
$env:LAB_LOGIN_ID=Read-Host '이전에 만든 테스트 일반 회원 loginId'
Get-Date -Format 'yyyy-MM-dd HH:mm:ss K'
kubectl get hpa member-hpa -n soldesk
kubectl get nodes
k6 run --vus 2 --duration 60s --summary-export "$evidence/SC-03-2vus.json" .tools/member-load.js
```

정상 요청 품질과 자원 여유를 확인한 경우에만 다음 단계로 갑니다. 예상하지 않은 5xx가 30초간 5% 이상이거나 서비스가 응답하지 않으면 Ctrl+C로 중단하고 원인을 확인합니다. 팀이 더 엄격한 중단 기준을 정하면 그것을 따릅니다.

```powershell
k6 run --vus 5 --duration 180s --summary-export "$evidence/SC-03-5vus.json" .tools/member-load.js
```

**관찰:** k6 요청 수·p95·예상 밖 실패율, member CPU·HPA targets·replica, Pending 이벤트, CA 로그, AWS EKS/EC2의 노드 수. HPA는 1~3개, 노드는 전체 4~5대 범위입니다. 이미 노드가 5대면 6대로 늘어날 수 없습니다.

```powershell
kubectl get hpa member-hpa -n soldesk
kubectl top pods -n soldesk
kubectl get pods -n soldesk -l app=member -o wide
kubectl get events -n soldesk --sort-by=.lastTimestamp
kubectl logs deployment/cluster-autoscaler -n kube-system --since=10m --tail=100
```

원하는 숫자를 만들려고 HPA·노드 상한을 임의로 바꾸지 않습니다. 확장하지 않았으면 CPU·requests·시간·여유 자원 근거로 이유를 기록합니다. **SC-03-scale-out:** 같은 시간대의 부하 출력·HPA·그래프·노드.

### 11-3. 종료·축소·동일 시간대 비교

k6 종료 후 CPU가 먼저 내려가고 안정화 정책에 따라 Pod·노드 축소는 늦게 진행될 수 있습니다. 5·10·20분 시점처럼 관찰 시각을 적습니다. 모니터링 배치·EBS AZ·최소 크기 때문에 노드가 4대로 돌아오지 않을 수 있으므로 직접 노드를 강제 삭제하지 않습니다.

```powershell
kubectl get hpa member-hpa -n soldesk
kubectl get nodes
./scripts/ops/Test-DeploymentHttps.ps1
Remove-Item Env:LAB_LOGIN_ID -ErrorAction SilentlyContinue
```

Grafana 시간 범위를 실험 시작~안정화로 고정해 **SC-03-scale-in**을 찍습니다. 실제 값으로 `부하 조건 → 지연/오류 → CPU → Pod → 노드 → 종료 후 상태` 표를 채웁니다. 자동 확장 여부와 부하 처리 품질을 각각 평가합니다.

## 12. SC-04 · DB 연결 차단 → 새 연결 실패·원복

**이 단계는 실제 DB 연결에 영향을 주는 합의된 장애 훈련입니다.** 같은 RDS를 사용하는 회원·상품·주문 기능에 영향을 줄 수 있으므로, 앞선 자료 저장·임시 Gateway 정리·작업 중단 조건·교차 확인자를 먼저 준비합니다. RDS를 삭제·중지하는 실습이 아닙니다.

### 12-1. GUI + 명령 · 변경 대상과 복구 경로 준비

1. RDS → final-ordermsa-db → Connectivity & security에서 SG를 엽니다.
2. MySQL 3306의 **EKS 보안그룹 source 규칙**을 확인합니다. 그룹 ID·규칙 ID·source SG·port·description을 비밀값 없이 캡처합니다. 다른 규칙은 수정하지 않습니다.
3. 두 번째 PowerShell에서 AWS 인증·Terraform init·validate·현재 plan이 정상인지 확인합니다. 복구 담당자가 같은 폴더·state에 접근할 수 있어야 합니다.

```powershell
aws sts get-caller-identity
terraform '-chdir=terraform' init
terraform '-chdir=terraform' validate
terraform '-chdir=terraform' plan
```

**복구 준비가 안 되면 차단하지 않습니다.** 지금 저장한 No changes 계획은 장애 후 복구 계획이 아닙니다. 복구 계획은 차단 후 실제 변경을 새로 읽어 만들어야 합니다.

### 12-2. GUI · 승인한 3306 인바운드 규칙 하나만 제거

EC2/VPC Security groups의 인바운드 편집에서 위의 정확한 규칙만 제거·저장합니다. 시작 시각을 기록합니다. **SC-04-blocked:** 대상 SG와 빠진 규칙·시각.

보안그룹은 stateful하므로 기존 추적 연결이 당장 끊기지 않을 수 있습니다. 즉시 모든 API가 실패하지 않아도 이상이 아닙니다. 새 연결을 구분해서 봅니다. [AWS 연결 추적 설명](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/security-group-connection-tracking.html)

### 12-3. 명령·웹·Grafana · 새 연결·앱 영향 관찰

합의한 점검 시간 안에서만 실행합니다. 임시 MySQL 클라이언트의 `--connect-timeout=5`로 새 TCP 연결 실패를 확인할 수 있습니다. 5단계와 같은 방법으로 클라이언트를 만들고, 비밀번호는 `-p` 입력창에 넣습니다.

```powershell
kubectl run db-block-probe -n soldesk --image=mysql:8.4 --restart=Never --command -- sleep 600
kubectl wait pod/db-block-probe -n soldesk --for=condition=Ready --timeout=120s
$dbEndpoint=terraform '-chdir=terraform' output -raw db_address
kubectl exec -it db-block-probe -n soldesk -- mysql --connect-timeout=5 -h $dbEndpoint -u admin -p -e 'SELECT 1;'
```

기존 앱 연결은 유지될 수 있습니다. **앱의 새 연결 실패까지 관찰하기로 합의한 경우만**, 현재 member Pod 이름을 조회해 그 한 개를 삭제하여 Deployment가 새 Pod를 만들게 합니다. 단일 member의 로그인·관리자 기능이 중단될 수 있습니다.

```powershell
kubectl get pods -n soldesk -l app=member
$memberPod=Read-Host '방금 확인한 member Pod 한 개의 정확한 이름'
kubectl delete pod $memberPod -n soldesk
kubectl get pods -n soldesk -l app=member
kubectl logs deployment/member-depl -n soldesk --tail=80
```

새 Pod가 DB 초기 연결 때문에 시작에 실패하면 Probe URL 자체가 열리지 않을 수 있습니다. 기존 Pod가 살아 있을 때 readiness/liveness 결과와 신규 Pod 기동 실패를 같은 상황으로 쓰지 않습니다. **SC-04-impact:** 새 연결 timeout·관찰한 앱 상태·API·로그·시각.

### 12-4. 명령 · Terraform으로 정확히 원복

몇 분 내 관찰을 마치고 먼저 복구합니다. 알림이 나올 때까지 일부러 장애를 길게 유지하지 않습니다.

```powershell
terraform '-chdir=terraform' plan '-out=db-recover.tfplan'
```

계획이 **외부에서 제거한 원래 3306 규칙의 복구**인지 확인합니다. 의도치 않은 DB 교체·삭제·다른 변경이 있으면 원인을 확인합니다. 정상 계획을 읽은 뒤 적용합니다.

```powershell
terraform '-chdir=terraform' apply db-recover.tfplan
kubectl rollout status deployment/member-depl -n soldesk --timeout=300s
./scripts/ops/Test-DeploymentHttps.ps1
kubectl delete pod db-block-probe -n soldesk
terraform '-chdir=terraform' plan
```

CrashLoop backoff가 남으면 규칙 복구·로그를 확인하고 다음 재시도를 기다립니다. 필요 시 **복구 후** 해당 실패 Pod만 다시 생성합니다. 콘솔에서 새 규칙을 중복 생성하고 state 소유가 어긋나게 만들기보다 Terraform으로 복구합니다.

사이트 로그인·상품·기존 주문을 재조회하고 SG·Argo·DB 연결·No changes를 확인합니다. 새 테스트 주문이 필요하면 새로운 키·주문 ID로 기록합니다. **SC-04-recovered:** 같은 기능 정상·원래 허용 범위·복구 시각. 비밀번호 회전 훈련과 구분합니다.

## 13. SC-05 · 별도 DB 복원 → 데이터·실제 앱 확인

**범위:** 원본 DB를 유지하고 다른 이름의 비공개 DB를 복원합니다. 그 DB를 별도의 상품 앱에서 읽어봅니다. 운영 DB_HOST·운영 앱·메일 소비자를 복원 DB로 바꾸지 않습니다. 추가 RDS·스냅샷·Pod 비용과 실습 후 정리를 함께 기록합니다.

### 13-1. 정상 기준 데이터와 스냅샷 시점

5단계의 읽기 클라이언트로 이번 상품 ID·재고·웹/API 주문·Outbox 이벤트를 다시 확인합니다. 스냅샷 전후 팀의 새 주문·상품 쓰기를 잠시 멈추고 기준 시각을 기록합니다. 기존 행사 데이터·다른 상품 수를 섞지 않습니다.

**GUI:** RDS → Databases → `final-ordermsa-db` 선택 → Actions → Take snapshot. 이름 `final-rehearsal-실제session`을 사용하고 available이 될 때까지 확인합니다. 태그 `Project=Final`, `Purpose=RestoreRehearsal`을 붙입니다. **SC-05-baseline:** 기준 ID·데이터·스냅샷 시각.

### 13-2. GUI · 다른 이름의 비공개 RDS 복원

RDS → Snapshots → 방금 snapshot → Restore snapshot을 엽니다.

| 항목 | 선택·대조 |
| :--- | :--- |
| DB identifier | `final-restore-실제session`, 원본과 다른 이름 |
| 인스턴스 | 원본과 호환되는 실습용 클래스·엔진 |
| VPC·DB subnet group | 원본과 같은 프로젝트 VPC·DB subnet group |
| Public access | No |
| VPC security group | 복구 완료된 원본 DB의 프로젝트 MySQL SG |
| 태그 | Project=Final·Purpose=RestoreRehearsal |
| 모니터링·스토리지 등 | 복원 기본값을 읽고 추가 비용 항목 확인 |

Restore 후 새 인스턴스 available과 **다른 endpoint**를 기록합니다. 원본의 available·endpoint가 유지되는지 비교합니다. **SC-05-restored:** 별도 DB 식별자·private·endpoint·시각.

복원 직후의 암호는 스냅샷 시점과 연결되며 현재 원본 Secret이 회전됐다면 같다고 가정할 수 없습니다. **복원 DB만** Modify → Credentials settings에서 실습용 새 관리자 암호를 설정하거나, 복원 DB가 별도로 관리하는 Secret이 있다면 그 자격증명을 확인합니다. 원본 DB·원본 RDS Secret을 바꾸지 않습니다. 엔진·복원 방식에 따라 표시되는 자격증명 선택지가 다르므로 원본 Secret ARN을 그대로 참조하도록 임의 구성하지 않습니다.

### 13-3. 명령 + MySQL · 복원 데이터 읽기

```powershell
$restoreEndpoint=Read-Host '복원한 final-restore-... DB의 endpoint'
kubectl run restore-inspect -n devops-lab --image=mysql:8.4 --restart=Never --command -- sleep 3600
kubectl wait pod/restore-inspect -n devops-lab --for=condition=Ready --timeout=180s
kubectl exec -it restore-inspect -n devops-lab -- mysql -h $restoreEndpoint -u admin -p ordermsa
```

### 13-4. 직접 작성 · 복원 DB를 읽는 별도 상품 앱

**이 단계를 해야 DB available·SELECT에서 한 걸음 더 나아가 실제 앱 사용을 확인할 수 있습니다.** 실제 product 이미지로 GET만 시험합니다. 주문 워커·메일 발송을 복원 DB에 연결하지 않고, 스키마 갱신·마이그레이션을 끕니다. 이 단계는 상품 읽기 검증이며 전체 쇼핑몰·결제 복원이 아닙니다.

필요한 내부 키만 임시 Secret으로 전달합니다. 원문을 출력·파일 저장하지 않습니다.

```powershell
$source=kubectl get secret my-app-secrets -n soldesk -o json | ConvertFrom-Json
$labSecret=@{apiVersion='v1';kind='Secret';metadata=@{name='lab-app-secrets';namespace='devops-lab'};type='Opaque';data=@{INTERNAL_SERVICE_TOKEN=$source.data.INTERNAL_SERVICE_TOKEN}}
$labSecret | ConvertTo-Json -Depth 8 -Compress | kubectl apply -f -
$source=$null; $labSecret=$null
```

복원 DB의 암호를 별도로 입력합니다. 다음은 하나의 Secret을 등록하는 작업이며 전체 환경을 구성하는 자동 실행 스크립트가 아닙니다.

```powershell
$secure=Read-Host '복원 DB의 새 관리자 암호' -AsSecureString
$plain=[System.Net.NetworkCredential]::new('', $secure).Password
$labDb=@{apiVersion='v1';kind='Secret';metadata=@{name='restore-db';namespace='devops-lab'};type='Opaque';data=@{DB_PW=[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($plain))}}
$labDb | ConvertTo-Json -Depth 8 -Compress | kubectl apply -f -
$plain=$null; $labDb=$null; $secure.Dispose()
$productImage=kubectl get deployment product-depl -n soldesk -o jsonpath='{.spec.template.spec.containers[0].image}'
```

VS Code에서 `.tools/restore-product.yaml`을 직접 만들고 image·DB_HOST의 REPLACE 부분 두 곳을 실제 값으로 바꿉니다. 비밀번호는 넣지 않습니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: restore-product
  namespace: devops-lab
spec:
  replicas: 1
  strategy: {type: Recreate}
  selector:
    matchLabels: {app: restore-product}
  template:
    metadata:
      labels: {app: restore-product}
    spec:
      automountServiceAccountToken: false
      containers:
        - name: product
          image: REPLACE_WITH_CURRENT_PRODUCT_IMAGE
          ports: [{containerPort: 8080}]
          resources:
            requests: {cpu: 100m, memory: 256Mi}
            limits: {cpu: '1', memory: 600Mi}
          env:
            - {name: DB_HOST, value: REPLACE_WITH_RESTORED_ENDPOINT}
            - name: DB_PW
              valueFrom:
                secretKeyRef: {name: restore-db, key: DB_PW}
            - name: INTERNAL_SERVICE_TOKEN
              valueFrom:
                secretKeyRef: {name: lab-app-secrets, key: INTERNAL_SERVICE_TOKEN}
            - {name: S3_BUCKET_NAME, value: final-product-images-193644343848-ap-northeast-2}
            - {name: SPRING_JPA_HIBERNATE_DDL_AUTO, value: 'none'}
            - {name: SPRING_JPA_GENERATE_DDL, value: 'false'}
            - {name: SPRING_FLYWAY_ENABLED, value: 'false'}
          startupProbe:
            httpGet: {path: /actuator/health/liveness, port: 8080}
            periodSeconds: 10
            failureThreshold: 18
          readinessProbe:
            httpGet: {path: /actuator/health/readiness, port: 8080}
            periodSeconds: 10
```

이 앱에는 원본 product IRSA를 lab namespace까지 확장하지 않습니다. 이 실습은 DB 상품 읽기만 확인하며 S3 업로드는 수행하지 않습니다. 기동 실패 시 로그·DB 자격증명·주소·resource를 먼저 확인하고 기존 운영 권한을 무조건 늘리지 않습니다.

```powershell
kubectl apply -f .tools/restore-product.yaml
kubectl rollout status deployment/restore-product -n devops-lab --timeout=300s
kubectl logs deployment/restore-product -n devops-lab --tail=60
kubectl port-forward deployment/restore-product -n devops-lab 18082:8080
```

Postman 새 환경에서 GET `http://127.0.0.1:18082/product/list`, GET `http://127.0.0.1:18082/product/이번ID`를 확인합니다. 이번 직접 연결은 Gateway를 거치지 않으므로 `/product-service` 접두어가 없습니다. 같은 상품·재고가 보이고 readiness가 정상인지 대조합니다. **SC-05-app:** 별도 endpoint를 쓰는 Deployment·GET 결과·기준 데이터.

### 14-3. 공개용 자료·GitHub 기록

4. VALIDATION에는 실제 날짜·버전·결과·근거, TROUBLESHOOTING에는 실제 발생한 증상·원인·조치·재검증을 반영합니다.
5. 본인이 만든 Grafana JSON은 민감정보·데이터 소스 주소·UID를 검토한 뒤 공개 위치를 정합니다. Postman 환경 전체 export로 인증값을 올리지 않습니다.
