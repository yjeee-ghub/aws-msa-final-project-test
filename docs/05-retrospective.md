# 설계 판단과 운영 한계

이 프로젝트는 신입 시스템·DevOps 엔지니어가 **기술의 역할, 설정 이유, 확인 방법**을 설명할 수 있는 범위를 목표로 합니다. 기능 소개는 [앱 처리 구조](11-delivery.md), 실제 성공 여부는 [검증 결과](VALIDATION.md)에 구분합니다.

| 선택 | 이유 | 남는 한계 |
| --- | --- | --- |
| Terraform 세 루트 | state 보관·AWS·클러스터 의존성 구분 | state와 실행 순서 관리 필요 |
| Helm + Kustomize | 운영 도구 패키지와 앱 선언 관리 역할 구분 | 도구별 소유 자원을 구분해야 함 |
| 승인 PR + digest | 검토한 이미지의 추적·재배포 | 이미지 보관·DB 호환성이 별도 필요 |
| 내부 일회용 러너 | 관리 API 접근 제한을 유지한 검사 | 생성·정리 자동화는 후속 과제 |
| OIDC + 역할 분리 | 장기 AWS 키 대신 작업별 임시 권한 | subject 변경 시 신뢰 정책 재검토 |
| Secrets Manager + ESO | DB 비밀번호를 Git 밖에서 관리 | 회전 후 앱 재시작·기능 검증 필요 |
| Outbox + SQS + DLQ | 주문 처리와 메일 발송의 일시 장애 분리 | 영구 실패의 운영 개입·중복 가능 구간 존재 |
| 단일 NAT·Single-AZ RDS | 실습 비용과 복잡도 조절 | AZ 장애에 대한 고가용성 한계 |

## 포트폴리오에서 설명할 근거

- 코드 검사 성공과 실제 서비스 검증 성공을 별도로 제시합니다.
- 어떤 권한을 부여했고 어떤 작업을 제한했는지 코드로 연결합니다.
- 오류 메시지뿐 아니라 이벤트·지표·복구 확인을 함께 제시합니다.
- 실제로 수행하지 않은 장애 주입·DB 복원·키 회전을 성공 사례로 적지 않습니다.

## 다음 운영 과제

GitHub App 연동, 일회용 러너 자동 공급·정리, DB 비밀번호 회전 실습, DLQ 원인 분석·선택 재처리, 별도 DB 복원 검증, 부하 중 교체와 롤백을 순서대로 확장할 수 있습니다. 각 과제는 실패 조건과 완료 기준부터 정합니다.
